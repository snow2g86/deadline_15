# 3D 캐릭터 → 2.5D 등각 시범 (pilot3d) 메모

작성 2026-10-21. 기존 게임 파일은 건드리지 않음. 1단계: 임시 사람(기본 도형 + 코드 뼈대)으로 파이프라인 검증. **2단계(9절): KayKit CC0 실제 모델·동작으로 교체 시험.**

## 2. 카메라 일치
2D 타일 = 96×48 (Iso.TW 48 · TH 24, 2:1). 방위각 45°, **고도각 = asin(TH/TW) = 30°** (정통 등각 35.26° 아님).
타일 한 변 = 1 유닛 = 67.882 px (= 48·√2), 높이 1 유닛 = 58.79 px (= 67.882·cos30°).
화면 = ((x−z)·48, (x+z)·24 − y·58.79). 월드 x=격자 c, z=격자 r. 카메라는 (+c,+r) 쪽에서 (−c,−r) 을 봄.
Camera3D 직교 `size = 뷰포트높이/(67.88·k)` (k = 화면 1px 당 그림 도트 수). 증명: `p3_01/02` (격자 오차 0.0002 px, 높이 1 유닛 상자도 일치).
유닛 발 = 타일 윗면 가운데에서 3px 위 (iso.gd 와 같음, `FOOT_LIFT`).

## 3. 렌더링 비용 (M3 Max · gl_compatibility · 실제 창 1280×720 · vsync 끔 · 지도 바닥 그림 없이 캐릭터만, 동작 walk)
캐릭터 1명 ≈ 4.4k 삼각형 ×2(외곽선 패스), 몸 메시 1 + 무기 + 방패 → 그리기 호출 6.
| 방식 | 1명 | 9명 | 27명 | 메모리(27명) | 비고 |
|---|---|---|---|---|---|
| 개별 SubViewport | 1.1 ms | 2.7 ms | **4.6~5.5 ms** (호출 144, 뷰포트 28) | 영상 39.9MB | 캐릭터마다 독립 |
| 아틀라스(공유 SubViewport) | 1.1 ms | 4.2 ms | **10.4 ms** (호출 118) | 영상 40.3MB | 예상과 반대로 더 느림 (아래) |
| 구워 두기(캐시, idle 8프레임×1방향) | 0.8 ms | 0.8 ms | **0.9 ms** (호출 28) | +12MB (k=1), +48MB (k=2) | 굽는 데 27명 340 ms |
빈 장면(캐릭터 0) = 0.94 ms. 즉 캐릭터당 증가분: 개별 ≈ 0.14~0.17 ms, 아틀라스 ≈ 0.35 ms, 구움 ≈ 0.
- 아틀라스 묶음 크기 실험 (27명): 27명/통 10.4 ms → 9명씩 10.2 → 3명씩 8.3 → 1명씩 5.5 ms. **한 SubViewport 에 많이 넣을수록 느림** (원인 미확인: 이 환경의 GL-on-Metal 에서 한 큰 렌더 대상에 스키닝 메시를 모은 비용으로 추정). 1명씩 가 가장 빨랐음. 정확한 GPU 시간은 compat 에서 0 으로 나와 못 읽음 → 프레임 시간 기준.
- k=2 (2배 촘촘) 도 시간 차이 거의 없음 (그리기 호출·삼각형 수가 지배, 화소 수가 아님). 영상 메모리만 +10MB.
- 한 명 walk 8프레임 × 8방향 구우면 약 4MB (k=1, 셀 112×128 RGBA, 2단계 재측정 값 — 1단계에 적었던 14MB 는 잘못), k=2 면 약 16MB.
- 동작 중인 캐릭터가 많지 않은 턴제에서는 "평소엔 구운 한 장/UPDATE_ONCE, 움직이는 1~3명만 라이브 SubViewport" 가 가장 쌈 (지금 구조로 바로 가능).
- **모바일 예상 (실측 불가)**: 삼각형 240k/프레임 + 뷰포트 28개는 타일형 GPU 에서 렌더 패스 28개(= 매번 버퍼 읽고 쓰기)라서 부담. 저사양 안드로이드 compat 에서 개별 방식 27명은 수 ms~10+ ms 가능성. 권장: 삼각형 캐릭터당 ≤2k(지금의 절반 이하, 외곽선은 후처리/셰이더로), 움직이는 유닛만 라이브, 나머지는 구움 또는 UPDATE_ONCE 아틀라스, 사양별 k=1 고정. 스키닝은 GLES3 에서 변환 피드백이라 라이브 캐릭터 수에 비례함.

## 4. 도트풍 품질 평가 (솔직히)
기존 2D 시트에서 뽑은 값: 윤곽 어두운 갈색 ≈ RGB(49,38,29)·두께 ≈ 1 화면 px (시트 2px × 0.516), 시트 한 장 고유 색 100~137(팔레트 PNG), 포화도 중간 이상.
맞춘 것: 윤곽선 색·1px 굵기(뒤집은 메시), 4단 명암(+차가운 그림자 색 섞기), 도트 크기 = 화면 1px, 최근접 확대, HSV 끊기(색조 24 · 채도 4 · 명도 6)로 색 수 줄임 → 3D 쪽 캐릭터당 고유 색 23~28개.
**다른 것**:
1. 그림 결이 다름. 2D 는 사람이 점 하나하나 찍은 뭉치(리벳·투구 틈·수염 결·옷 주름)가 있고 색이 100개 이상. 3D 는 매끈한 면 + 4톤이라 "인형" 같음. 같은 키에서 차지하는 화소 수도 2D 의 약 40%(약 1300 vs 3000) → 가로로 1.2배 통통하게 키웠음(`CHUNK`).
2. 얼굴·손 같은 작은 디테일은 도형으로는 안 나옴 (눈 1~2px). 실제 모델·텍스처 필요.
3. 게임 팔레트 32색 강제 맞추기는 **나쁨**: 옷 색이 갈색·회색 쪽으로 쏠려 정체성을 잃음(사진 p3_10 V3). RGB 채널별 끊기도 회색이 푸르게 틀어져 못 씀 → HSV 끊기 채택.
4. 앞으로 개선 여지: 텍스처가 입혀진 모델 + 팔레트 램프(색마다 4톤 램프)를 아티스트가 지정, 컷아웃 같은 외곽 뭉침(후처리 팽창·침식), 모델에 더 굵은 실루엣. 현재 판정: **"같은 게임에 섞어 놓으면 눈에 띄게 다름"**. 3D 전용 캐릭터로 통일한다면 쓸 만하고, 2D 와 섞는 건 비추천.

## 5. 부품 슬롯 구조
- 스킨 부품(`hair face top bottom shoes helm cape`): 같은 뼈대를 공유하는 스킨 메시. 캐릭터마다 선택된 부품을 **하나의 ArrayMesh 로 합침** (그리기 호출 절약). 부품은 도형 목록 데이터(`p3_parts.gd` DB)라 JSON 으로 빼기 쉬움.
- 소켓 부품(`weapon shield`): `BoneAttachment3D`(RightHand / LeftHand) + 오프셋 (`p3_rig.gd` SOCKETS).
- 부품 수: 머리 4 · 얼굴 4 · 윗옷 3 · 하의 3 · 신발 3 · 투구 3(+없음) · 망토 2(+없음) · 무기 4(+없음) · 방패 3(+없음).
- 색: 셰이더 채널(피부·머리카락·옷1·옷2·금속·가죽·나무·눈·흰색·볼) uniform. 피부 6 · 머리 8 · 옷(주·보조 쌍) 8 · 금속 4.
- **저장 형식 제안**: `{"v":1, "s":{"hair":2,"face":1,"top":0,"bottom":1,"shoes":0,"helm":0,"cape":1,"weapon":1,"shield":2}, "c":{"skin":1,"hair":4,"cloth":3,"metal":0}}` — 슬롯별 부품 번호(선택 슬롯 0 = 없음), 색 번호. 문자열 `"1:2.1.0.1.0.0.1.1.2|1.4.3.0"` 로도 묶음. `v` 로 버전, `sanitize()` 가 범위 밖 값을 고쳐 옛/깨진 저장도 읽힘. 번호는 **재배열 금지·뒤에만 추가**(저장 호환). 직업은 따로 두고 외형만 이 값.
- 무작위: `Look.random_look(rng)` (시드 고정 가능).

## 6. 실제 glTF 모델로 바꿔 끼우는 절차
1. **뼈대 이름 매핑**: `p3_rig.gd` 의 BONES 이름이 표준(Hips Spine Chest Neck Head Left/RightUpperArm·LowerArm·Hand, Left/RightUpperLeg·LowerLeg·Foot). 받은 모델이 Mixamo(`mixamorig:Hips`…)·VRM 등이면 `BONE_MAP = {우리이름: 모델뼈이름}` 표를 만들어 Godot `SkeletonProfileHumanoid` + BoneMap 으로 리타깃 (임포트 설정 "Retarget → Bone Map"), 또는 이 표로 find_bone. 뼈가 더 많아도 됨(손가락 등) — 우리 코드는 위 17개만 직접 만짐.
2. **임시 사람 빼기**: `P3Char` 에서 `Rig.build_skeleton()`·`apply_look` 의 메시 합치기 부분을 "glb 장면 인스턴스 + 부품 glb 를 같은 Skeleton3D 아래에 붙임(MeshInstance3D.skeleton)"으로 교체. 스킨 메시 부품은 모델의 같은 뼈 이름을 쓰는 한 그대로 같은 뼈대에 붙음.
3. **슬롯 부착점 지정**: 소켓은 `Rig.SOCKETS` 의 뼈 이름·오프셋만 바꿈(손 소켓 뼈 = `RightHand`/`LeftHand`, 필요하면 머리 소켓 `Head` 에 투구, 등 `Chest` 에 망토). 무기 glb 는 "쥐는 곳이 원점, +Y 가 날 쪽" 으로 내보내기 약속을 두고 Blender 에서 맞춤. 머리·투구 부품은 같은 뼈대를 쓰는 스킨 메시이거나 `Head` 소켓.
4. **동작 이름 매핑**: `p3_anims.gd` 의 NAME_MAP `{우리이름: 모델 애니메이션 이름}`. 표준 이름 idle / walk / attack / hit. 받은 AnimationPlayer 라이브러리를 `P3Char.player` 에 `add_animation_library("", lib)` 하고 이름만 이어 붙임. 길이·루프 정보는 애니메이션 자신이 가짐(LEN/LOOP 대신). 공격 타격 시점은 애니메이션 트랙 호출(메서드 트랙) 또는 `hit` 시각 표에 넣어 `sprite_db` 의 `hit` 와 맞춤.
5. **재질**: 모델 텍스처를 쓸 때는 `toon.gdshader` 의 `pick(ch)` 대신 `texture(ALBEDO_TEX)` 를 읽고 셀 단계/외곽선(`outline.gdshader`)은 그대로. 외곽선은 `TANGENT.xyz` 에 부드러운 바깥 방향이 필요(지금은 조각 중심 기준으로 만들어 넣음) → 실제 모델은 임포트 시 스무스 노멀을 굽거나 후처리 외곽선(`post.gdshader outline_on`)으로 대체.
6. 크기: 키 0.86 유닛(발~머리끝) = 화면 몸 50px 에 맞춰 스케일. `CHUNK` 로 가로 굵기 조정.
7. 사진 기준 비교(`--auto --only=compare`)를 다시 돌려 외곽선 굵기·명암 단계·색 끊기를 재조정.

## 7. 24종을 3D 로 옮길 때 필요한 것과 위험
필요: ① 24종(남/여 구분 시 더 많음) 모델 또는 부품 세트 + 직업별 대표 장비(검·방패·활·지팡이·총? 현재 부품엔 활 없음) ② 동작 4종(+이동·사망·스킬 시전·방어 등 직업별) 표준 뼈대에 맞춘 라이브러리 ③ 방향은 3D 회전으로 해결(뒷모습 별도 작업 불필요 — 지금 2D 의 4방향 뒷모습 파이프라인이 사라짐) ④ 스프라이트 캐시 정책(움직이는 유닛만 라이브) ⑤ 도트 맞춤 셰이더 튜닝과 아티스트 기준 사진 ⑥ 기존 공격 효과(시트 `hit` 타이밍, 공격 임팩트 위치)를 3D 손/무기 뼈 위치로 다시 연결.
위험: ● **그림 결이 2D 와 안 맞음** (위 평가) — 전부 3D 로 통일하거나 영구히 둘을 분리해야 함. ● 외부 모델 라이선스·스타일 통일·뼈대 규격(리타깃 품질). ● 모바일 라이브 SubViewport 비용(위 3절). ● 부품 조합 폭발 → 모든 조합에서 관통(머리카락-투구, 망토-갑옷) 검수 필요, 부품마다 "숨길 몸 부위" 표 필요. ● 소환수 등 사람형이 아닌 적(몬스터)은 별도 뼈대. ● 캐릭터 커스터마이징 저장·서버 검증(번호 범위). ● 파일 크기: 모델 수 증가 + 텍스처. ● 공성아이템·지형과 앞뒤 가림(스프라이트 y 정렬은 되지만 큰 무기가 타일 밖으로 나갈 때 깊이 순서 오류 가능).

## 8. 사용자가 정할 것
1. 3D 와 2D 를 **섞을지, 3D 로 통일할지**(섞기엔 지금 그림 결 차이가 큼).
2. 살릴 모델의 **스타일**(로우폴리 + 텍스처 도트 / 손그림 텍스처 / 지금처럼 단색 셀) — 도트 느낌은 모델 쪽 텍스처가 더 좌우함.
3. 모바일 목표 사양(구기종 포함 여부) → 라이브 3D 캐릭터 수 상한과 k 값.
4. 커스터마이징 범위(얼굴 모양·체형 포함? 슬롯만?) 와 직업 장비 고정 여부.
5. 외부 재료 다운로드 허락(별도 조사 결과 기준) 과 라이선스 허용 범위.

## 9.3 뼈대·동작 구조 (리타게팅 필요 없음)
- 캐릭터 6종 모두 **같은 뼈대 `Rig_Medium`**(23뼈): root hips spine chest, upperarm/lowerarm/wrist/hand/**handslot**(.l/.r), head, upperleg/lowerleg/foot/toes(.l/.r). 목(neck) 뼈 없음. 동작 묶음도 같은 뼈 이름의 트랙(`Rig_Medium/Skeleton3D:<뼈>`) → 캐릭터 루트 아래 AnimationPlayer 의 root_node 만 모델 노드로 맞추면 그대로 재생됨 (실제로 확인).
- 따라서 1단계의 "뼈대 이름 매핑표(BONE_MAP)"는 **필요 없었음**. 우리 임시 뼈대(Hips Spine…)와는 이름이 다르므로(hips·upperarm.l 등) 임시 뼈대 코드는 쓰지 않고 `p3b_char.gd` 가 따로 처리.
- 무기·방패는 소품 gltf 를 `handslot.r`(무기)·`handslot.l`(방패) 뼈에 **BoneAttachment3D** 로 붙임. 소품은 그대로 손에 맞게 모델링돼 있어 오프셋 조정 없이 맞음(한손검·도끼·단검·지팡이 확인. 활·석궁은 모양은 붙지만 아래 한계 참고).
- **동작 이름 매핑** (우리 표준 → KayKit): idle→`Idle_A`(양손무기 `Melee_2H_Idle`, 활 `Ranged_Bow_Idle`), walk→`Walking_A`, run→`Running_A`(활 `Running_HoldingBow`), hit→`Hit_A`(`Hit_B`), block→`Melee_Block`, death→`Death_A`, cast→`Ranged_Magic_Spellcasting`, **attack 은 무기로 정함**: 한손검·도끼=`Melee_1H_Attack_Chop`, 단검=`Melee_1H_Attack_Stab`, 양손=`Melee_2H_Attack_Chop`, 활=`Ranged_Bow_Release`, 석궁=`Ranged_2H_Shoot`, 지팡이·마법봉=`Ranged_Magic_Shoot`, 맨손=`Melee_Unarmed_Attack_Punch_A`. 함수 `P3bChar.resolve()`.
- 받은 동작 수 (Medium 뼈대): General 15(대기A/B·피격A/B·죽음A/B·상호작용·던지기…), MovementBasic 11(걷기A/B/C·달리기A/B·점프5), MovementAdvanced 13(웅크림·기기·회피4·달리기 활/소총·옆달리기·뒷걷기), CombatMelee 22(한손 5·양손 5·**방패 막기·막고 치기·막기 피격**·쌍검 3·맨손 4), CombatRanged 20(활 9·마법 6·소총/석궁 5), Special 15(스켈레톤용), Tools 29, Simulation 14. **우리가 쓰는 4종(idle walk attack hit)은 전부 있음**, 달리기·막기·시전·죽음도 있음.
- **부족한 동작**: 피격이 방향별(앞·뒤·옆)로 없음(2종뿐), 활 시위 당김+발사가 두 동작으로 나뉘어 있어 한 "공격"으로 합치려면 이어 붙이기 필요, 마법 "시전 후 폭발" 같은 직업 스킬 전용 동작 없음, 방패+한손검 전용 공격은 `Melee_Block_Attack` 한 가지, **야만전사처럼 큰 체형(Rig_Large)용은 유료 판에 더 많음**(Large 뼈대는 이번 몸 5종에선 안 씀).
- 동작 길이: 대기 1.07s, 걷기 1.07s, 한손 공격 1.07s, 피격 0.67s — 우리 임시 동작(0.5~0.8s)보다 길어 턴제 연출에서는 속도 배율(speed_scale)로 줄이는 게 낫다.

## 9.4 몸(머리·옷 통째)을 슬롯 하나로 — 구조와 한계
저장 형식 v2: `{"v":2,"s":{"body":2,"helm":1,"cape":1,"weapon":3,"shield":1},"c":{"skin":1,"hair":4,"cloth":3,"metal":0}}` (문자열 `"2:2.1.1.3.1|1.4.3.0"`). `body` = 6종 중 하나(머리·옷·팔·다리 메시가 한 묶음), `helm`/`cape` = 해당 메시 켜고 끄기, `weapon`/`shield` = 소품 번호(무기 9종+없음, 방패 5종+없음). v1(임시 사람)과 형식 버전으로 구분.
구현: 몸 glb 를 템플릿으로 한 번만 읽어 복제, 보이는 메시들을 **하나의 스킨 메시로 합침**(그리기 호출 24→8, 아래 성능). 메시마다 이름 규칙(`*_Helmet`, `*_HelmetVisor`, `*_Hat`, `*_BearHat`, `*_Mask`, `*_Cape`)으로 슬롯 판별.
- **되는 것**: 몸 6종 교체, 투구·모자·마스크 끄기(끄면 맨 머리 — 기사는 금발 머리가 따로 모델링돼 있음), 망토 끄기, 무기·방패 소품 자유 조합.
- **한계**: ① 머리(헤어스타일)와 얼굴·옷이 **몸에 묶여 따로 못 바꿈**(머리 모양 4종 같은 건 불가, 직업 5종 = 헤어 5종). 헤어는 색만. ② 투구를 벗을 때 기사만 맨머리가 있고, 야만전사·마법사·궁수의 "모자/후드"를 벗은 머리가 항상 자연스러운지는 직업마다 다름(마법사 모자 벗은 얼굴은 사진 p3b_09). ③ 몸 체형은 Medium 하나(Large 몸은 유료판). ④ 옷 갈아입기(윗옷·하의 조합)는 **불가능** — 몸 하나가 한 벌. 조합 폭발 대신 "몸 6 × 투구 2 × 망토 2 × 무기 9 × 방패 6 × 색" 정도. ⑤ 2손 무기+방패, 활+방패 같은 조합은 동작(팔 위치)과 소품이 서로 안 맞아 뚫림/어긋남(소품 위치는 손 뼈에 붙을 뿐 동작은 무기별 전용) → 조합 규칙(허용표) 필요. ⑥ 소품 `shield_*`·`sword_*` 의 "color" 판은 색이 고정(아틀라스 칸).

## 9.5 색 바꾸기 (머리색·옷색)
모델 질감은 **가로 8 × 세로 4 칸 팔레트 아틀라스**(1024², 칸마다 세로 그라데이션 128×256). 메시가 칸에 UV 를 얹는 구조라서 **UV→칸 번호로 마스크 없이** 칸 단위로 색을 바꿀 수 있음. 몸마다 칸의 역할이 같아서 규칙을 찾음: 칸(0,0)=피부 전 캐릭터 공통, 칸(1,0)=머리카락 전 캐릭터 공통, 칸(0,1)=옷 주색(기사 빨강 망토·마법사 보라·궁수 파랑·도적 청록), 도적은 (1,1)=옷 보조색 등 — 몸별 표 `P3bLook.ROLES`. 셰이더가 칸마다 "역할 번호"와 칸 평균 밝기를 받아 `새 색 × (원래 밝기 / 칸 평균 밝기)` 로 그라데이션을 유지한 채 색만 바꿈.
- **가능**: 피부 6 · 머리카락 8 · 옷 주/보조 8쌍, 기사는 금속(갑옷) 색 4종(원래/금/청동/어두운 강철). 사진 `p3b_07_looks9`, `p3b_08_colors_*`.
- **한계**: ① 칸이 의미 단위가 아님: 한 칸이 옷·가죽·장식에 같이 쓰이면 한꺼번에 바뀜(궁수 보조색을 금색으로 하면 튜닉 전체가 노란색, 사진 p3b_09). 몸마다 역할표를 사람이 정해야 함(자동 판별은 불가 — 칸 색만으론 모름). ② 기사 갑옷은 철색 1칸이 대부분이라 옷색 쌍과는 무관, 금속색을 따로 둠. ③ 그라데이션 비율 방식이라 금색 같은 밝은색은 평평해 보임. ④ 소품(무기·방패)은 몸과 같은 재질(몸 질감)로 그림 — 소품 UV 의 칸 배치가 몸 팔레트와 거의 같아 대체로 맞게 보이지만 소품 전용 질감(rogue/ranger 파일)을 따로 읽지는 않아 색이 어긋난 소품이 있을 수 있고, 몸의 색 바꾸기 칸 규칙이 소품에도 같은 칸 번호로 적용됨(소품 색은 의도한 제어 대상이 아님, 미검증). ⑤ 텍스처 자체를 다시 그리지 않는 한 무늬(문장 등) 변경은 불가.

## 9.6 도트풍 후처리 — 실제 모델 결과
설정: 셀 4단, 윤곽선 1px(뒤집은 메시, 스무스 노멀을 TANGENT 에 구워 넣어 로우폴리 모서리에서도 안 찢어짐), HSV 끊기(명도 6), **칸 안 그라데이션 3단 끊기**(`tex_levels=3`, 텍스처를 단순화하는 방식). 사진 `p3b_02_post_variants`(A 원본 / B +HSV / C 그라데이션 3단 / D 칸마다 한 색).
**가설 확인 — 모델 텍스처가 도트 느낌을 크게 좌우한다: 맞음.** 1단계 임시 사람(단색 도형)보다 같은 후처리로 훨씬 게임답게 보임: 마법사 보라 로브·갑옷 리벳·얼굴(눈·눈썹)이 모델 질감에서 와서 2D 와 섞였을 때 "캐릭터" 느낌이 남. 텍스처 해상도 자체는 의미 없음(8×4 칸의 세로 그라데이션이라 해상도를 낮춰도 같음) → 대신 **칸 안 그라데이션을 3단으로 끊는 게** 효과적(C): 도트 군집처럼 보임. 1칸=한 색(D)은 밋밋해 비추천. 4가지는 화면에서 거의 구분이 안 될 정도로 차이가 작음(전투 크기 기준) — 즉 후처리는 모델 선택보다 영향이 작음.
**2D 와 나란히** (`p3b_03_compare_*`, `p3b_04_battle_size*`): 실제 전투 크기(줌 1)에서 3D 캐릭터는 2D 와 **같은 급으로 읽힘**(머리·무기·색 구분 가능, 몸 높이 0.75 유닛 ≈ 화면 44px 로 2D 몸 50px 에 맞춤). 좋은 점: 윤곽선·팔레트 느낌·도트 크기가 비슷, 8방향 회전·동작 4종이 공짜. 어색한 점: ① 3D 쪽 머리가 크고 몸이 짧은 "치비" 비율이라 2D 의 성인 비율(기사 중갑)과 체형이 다름, ② 2D 는 점마다 손으로 찍은 명암(리벳·투구 틈·수염 결·색 100+)이라 질감이 풍부, 3D 는 4톤+단순 칸 색이라 단조로움, ③ 얼굴 표정이 눈 2점뿐이라 작아지면 읽히는 건 몸 실루엣·색뿐, ④ 어두운 갈색 윤곽선이 2D 보다 약간 굵게(균일하게) 보임, ⑤ 같은 키에서 3D 가 차지하는 화소 수가 2D 와 비슷해져 크기 문제는 해결(1단계 임시 사람은 40%였음).
**전투 크기에서 쓸 만한가**: 줌 1 에서 직업(기사·마법사·야만전사·궁수)을 구분할 수 있고 방향별 무기 위치도 읽힘. 방패는 바깥쪽 몸에 가려 안 보이는 방향이 있음(2D 도 마찬가지). 작은 소품(마법봉·단검)은 줌 1 에서는 1~2px 선이라 읽기 어려움.

- **메시를 하나로 합치면 약 5~6배 빨라짐**(같은 부하에서 118~130 ms → 7~23 ms). KayKit 는 몸을 9조각으로 나눠 놓아서 합치지 않으면 임시 사람(6호출)의 4배 호출이 나옴. 합친 뒤엔 임시 사람과 같은 수준(삼각형은 1.5배 많음).
- 구운 그림(캐시) 방식: 27명 idle 8프레임×1방향 = 12MB(k=1) / 48MB(k=2), 프레임 시간은 사실상 빈 장면과 같음(1.35 ms). 굽는 시간은 합친 뒤 27명 약 0.9초(부하 시 1.8초) → 로딩 화면에서 미리 굽거나 캐릭터별로 필요할 때만. 한 명 8프레임×8방향 = 약 4MB.
- 1단계 결론 유지: **한 SubViewport 에 많이 묶는 아틀라스가 개별보다 오히려 느림(27명 13 ms 대 7 ms)**, 턴제에선 움직이는 1~3명만 라이브, 나머지는 구운 그림이 가장 쌈. 메모리: 영상 메모리 27명 약 140MB(질감 6장 + 뷰포트) — 모바일에선 질감 5장×1024²를 256²로 줄이는 것(칸 구조라 문제 없음)과 삼각형 절반 이하로 줄이는 것 필요.
- **모바일 예상(실측 아님)**: 호출은 합치면 8/명으로 문제 없으나 삼각형 40만/프레임(외곽선 패스 포함)과 스키닝(GLES3 변환 피드백)·뷰포트 28개 렌더 패스가 타일형 GPU 에 부담 → 라이브 캐릭터 수를 화면 내 3~6명으로 제한 + 나머지 구운 그림이 현실적. 외곽선은 후처리(실루엣만)로 바꾸면 삼각형 절반.

## 9.9 24종(직업 12 × 남녀)을 이 방식으로 옮길 때의 현실성·위험
- **현실성: 중간.** 파이프라인(읽기·동작 재생·소품 부착·색 바꾸기·후처리·스프라이트 합성·8방향)은 이번에 전부 돌아감. 그러나 Free 판은 **캐릭터 5종**이라 24종 중 절반 이상(사제·창병·망치병·샤먼·공병·암살자·소환사 등)이 없음 → 직접 모델링/구매(Extra·다른 팩)/AI 생성 중 하나가 필요하고, 체형·스타일을 한 팩으로 통일해야 함.
- **남녀 구분 없음**: KayKit 몸은 중성 치비. 현재 2D 는 직업마다 남(01)·여(02) 그림이 따로 있음 → 3D 로 오면 헤어/얼굴 색 구분 정도로 단순화되어 **캐릭터 개성이 사라질 위험**(이름 있는 인물이 있는 스토리 연출과 충돌).
- **그림 결 불일치**: 스타일이 "귀여운 로우폴리 치비" ↔ 현재 2D 는 "성숙한 중갑 도트". 섞으면 위화감, 전부 3D 로 가려면 몬스터·적·소환수도 같은 스타일 필요(몬스터는 별도 뼈대).
- **동작 연결**: 현재 `sprite_db` 의 직업별 hit 프레임·공격 시점(예: knight attack hit=8프레임)을 KayKit 동작 길이로 다시 맞추고, 스킬 이펙트 위치를 손/무기 뼈(handslot) 월드 위치에서 가져오는 일이 필요(좋은 점: 뼈 위치로 정확히 연결 가능).
- **조합 폭발 검수**: 몸×투구×망토×무기×방패 조합마다 관통/손 위치 검수 → 허용표 필요(양손무기+방패 금지 등).
- **성능**: 합치기 필수, 라이브 캐릭터 수 제한, 구움 캐시 정책, 모바일은 모델 삼각형 절반.
- **라이선스**: CC0 라 안전하나 "파는 콘텐츠를 재판매 금지(수정 안 한 원본 그대로)" 문구 있음(원본 묶음 재배포 금지) — 게임 안에 포함해 배포는 허용. 다른 팩을 더 받을 땐 각각 확인.
- **한 줄 평가**: 임시 사람 단계의 "인형" 느낌은 실제 모델로 상당히 해소됨. 하지만 **지금 24종 2D 를 대체**하기엔 모델 수·성별·체형·스타일이 모자라고, 도트 느낌은 모델의 질감 품질에 달림.

## 9.10 사용자가 결정할 것 (2단계)
1. **스타일 방향**: KayKit 풍(밝고 둥근 치비 3D) 으로 가도 되는지, 지금의 어두운 중갑 도트 느낌을 유지해야 하는지 — 유지가 필요하면 KayKit 는 맞지 않고, 스타일이 맞는 다른 모델 팩/직접 제작이 필요.
2. **커스터마이징 범위**: 머리 모양·옷 갈아입기까지 원하는지(그러면 몸 통째 교체형으로는 불가 → 부품 분리형 모델이 필요), 아니면 "몸 6종 + 색 + 장비" 정도로 충분한지.
3. **2D 와 3D 혼용**: 신규 캐릭터(커스터마이징 대상)만 3D, 기존 24종은 2D 유지(혼용) vs 전부 3D. 혼용이면 전투에서 한 화면에 섞임(사진 p3b_04).
4. **남/여 구분과 직업 개성**: 3D 에서 어떻게 표현할지.
5. **모바일 목표 사양**(라이브 3D 수 상한, 질감 크기, 삼각형 예산).
6. 유료 Extra/다른 팩 구매·다운로드 허락 여부(캐릭터 수 확충). 이번엔 허락된 무료 2개만 받음.
7. 실제로 진행한다면 `Rig_Large` 야만전사·유료 체형, 무기 조합 허용표, 방향별 피격 동작 추가 제작 여부.
